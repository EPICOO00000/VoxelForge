==============================================================================
CODING STANDARDS — DOCUMENTATION
==============================================================================

Documentation must make VoxelForge behavior understandable without requiring
developers to reverse-engineer implementation details.

Documentation should describe stable behavior, important constraints and
developer-facing contracts.

==============================================================================

GENERAL PRINCIPLE

Documentation must be:

Accurate.

Clear.

Maintained.

Specific.

Consistent with the implementation.

Outdated documentation is a defect and should be corrected when discovered.

==============================================================================

PUBLIC APIs

Public APIs must document behavior that another subsystem or plugin needs to
use the interface correctly.

Documentation should cover:

Purpose.

Inputs.

Outputs.

Errors.

Ownership.

Lifetime.

Threading.

Side Effects.

Compatibility Requirements where relevant.

==============================================================================

IMPLEMENTATION COMMENTS

Implementation comments should explain why code behaves a certain way when the
reason is not obvious from the implementation.

Avoid comments that simply translate code into natural language.

==============================================================================

ARCHITECTURAL DOCUMENTATION

Important architectural decisions should be documented in the appropriate
specification or design documentation rather than hidden only inside source
comments.

Documentation should identify subsystem ownership and allowed dependencies.

==============================================================================

PERFORMANCE DOCUMENTATION

If an API has important performance characteristics, document them.

Examples include:

Whether an operation allocates memory.

Whether it operates synchronously.

Whether it processes complete worlds or individual chunks.

Whether an operation may be expensive for large worlds.

==============================================================================

THREADING DOCUMENTATION

APIs with thread restrictions must document them explicitly.

For example, documentation should state when an operation:

Requires the UI thread.

May run on a worker thread.

Is thread-safe.

Must not be called concurrently.

==============================================================================

OWNERSHIP DOCUMENTATION

If an API returns an object whose lifetime is controlled by another subsystem,
that ownership must be documented.

Plugins and other callers must not assume ownership unless the API explicitly
grants it.

==============================================================================

FILE FORMAT DOCUMENTATION

Import/export implementations must document format-specific behavior and
limitations.

This includes Minecraft and Bloxd.io compatibility.

For Bloxd.io `.bloxdschem`, documentation must clearly state that a single
schematic is limited to 200 chunks.

Larger exports must be divided into multiple schematic files rather than
truncated.

==============================================================================

EXAMPLES

Examples should demonstrate valid API usage.

Examples must remain compatible with the current documented API.

Outdated examples are particularly dangerous because developers often copy
example code directly into production code.

==============================================================================

NAMING IN DOCUMENTATION

Use the same terminology as the source code and architecture specifications.

Do not use multiple names for the same subsystem or concept.

==============================================================================

CHANGE DOCUMENTATION

Changes to public behavior should be documented when they affect:

Compatibility.

API contracts.

File formats.

Plugin behavior.

Performance expectations.

Threading.

Security.

==============================================================================

DEPRECATION

Deprecated APIs must clearly identify:

That they are deprecated.

Why they are deprecated when useful.

What should be used instead.

Any migration requirements.

==============================================================================

DOCUMENTATION LOCATION

Documentation should be placed in the appropriate repository location.

Do not duplicate the same authoritative specification across unrelated files.

When duplication is necessary for discoverability, one source should remain
clearly authoritative.

==============================================================================

ACCURACY

Documentation must never intentionally describe behavior that the
implementation does not provide.

If the implementation and specification disagree, the discrepancy must be
resolved rather than silently ignored.

==============================================================================

DESIGN OBJECTIVE

A developer should be able to understand how to correctly use a VoxelForge API
from its documentation without depending on undocumented implementation
details.

==============================================================================

END OF CODING STANDARDS — DOCUMENTATION
