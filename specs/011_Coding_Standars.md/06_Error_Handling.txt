==============================================================================
CODING STANDARDS — ERROR HANDLING
==============================================================================

VoxelForge must handle failures explicitly and predictably.

Error handling exists to protect application stability, world correctness,
plugin isolation and user data.

==============================================================================

GENERAL PRINCIPLE

Errors must never be silently ignored when they can affect correctness.

Every subsystem must follow the error-handling model appropriate to its
language and architecture.

==============================================================================

ERROR CATEGORIES

Errors should distinguish between situations such as:

Invalid User Input.

Invalid File Data.

Unsupported Format.

Missing Resource.

I/O Failure.

Plugin Failure.

Configuration Error.

Internal Logic Error.

Resource Exhaustion.

Cancellation.

==============================================================================

VALIDATION

Input must be validated at subsystem boundaries.

Validation is particularly important for:

File Data.

Coordinates.

Dimensions.

Block Identifiers.

Chunk Identifiers.

Plugin Data.

Configuration.

Import Options.

Export Options.

UI Input.

==============================================================================

ERROR PROPAGATION

Errors should be propagated to the layer capable of handling them appropriately.

Low-level code should not hide failures merely to simplify its caller.

Higher-level systems should provide appropriate user-facing or diagnostic
feedback when necessary.

==============================================================================

USER-FACING ERRORS

Errors shown to users should be understandable and actionable where possible.

Technical implementation details should not overwhelm normal user-facing
messages.

Detailed diagnostic information may be provided through logging or developer
diagnostics.

==============================================================================

LOGGING

Errors that require investigation should provide useful diagnostic information.

Logs should contain enough context to identify:

What operation failed.

Which subsystem failed.

Relevant resource or operation information.

The failure reason.

Sensitive information must not be logged unnecessarily.

==============================================================================

EXCEPTIONS / ERROR VALUES

Use the project's established error mechanism consistently.

Do not mix incompatible error-handling patterns without a clear architectural
reason.

Exceptions or equivalent mechanisms must not be used as ordinary control flow
unless the language and project conventions explicitly support that pattern.

==============================================================================

RESOURCE CLEANUP

Resources must be released correctly when an operation fails.

This includes:

Files.

Memory.

Tasks.

GPU Resources.

Temporary Data.

Plugin Registrations.

Event Subscriptions.

Locks.

==============================================================================

PARTIAL OPERATIONS

Operations that can partially modify data must define what happens when they
fail.

World-editing operations should use the appropriate transaction, history or
batch mechanisms to avoid leaving the world in an invalid state.

==============================================================================

IMPORT FAILURES

Importers must validate external files before performing irreversible world
changes where practical.

Malformed or unsupported files must not corrupt existing world data.

==============================================================================

EXPORT FAILURES

Export failures must not be reported as successful exports.

Partially written output must be handled according to the format and export
contract.

Temporary files should be cleaned up where appropriate.

==============================================================================

BLOXD.IO

Bloxd.io schematic exports must respect the 200-chunk maximum per schematic.

If an export is split into multiple `.bloxdschem` files and one part fails, the
export system must report the failure clearly rather than claiming that the
complete export succeeded.

==============================================================================

PLUGIN ERRORS

Plugin errors must be isolated from unrelated core systems whenever possible.

A failing plugin must not silently corrupt world data or leave permanent
registrations behind.

Plugin lifecycle cleanup must still occur after failure when technically
possible.

==============================================================================

THREADING ERRORS

Errors occurring in worker tasks must be propagated through the project's task
and error-reporting mechanisms.

Worker-thread failures must not directly manipulate UI state unless the API
explicitly permits it.

==============================================================================

CANCELLATION

Cancellation is not necessarily an error.

Operations that support cancellation should distinguish cancellation from
unexpected failure when the API allows it.

Cancelled operations must still release resources correctly.

==============================================================================

RECOVERY

Where recovery is possible, it should be explicit.

The application must not silently continue with corrupted or incomplete state
simply because an error was encountered.

==============================================================================

ASSERTIONS

Assertions may be used to detect programmer errors and violated internal
invariants.

Assertions must not replace validation of untrusted external input.

==============================================================================

DESIGN OBJECTIVE

Error handling must preserve correctness first, provide useful diagnostics
second and maintain a predictable experience for users and developers.

==============================================================================

END OF CODING STANDARDS — ERROR HANDLING
