==============================================================================
CODING STANDARDS — REFACTORING
==============================

Refactoring is the controlled improvement of existing code without changing its
intended external behavior.

==============================================================================

GENERAL PRINCIPLE

Refactoring should improve one or more of:

Readability.

Maintainability.

Correctness.

Testability.

Performance.

Architecture.

A refactor must not introduce unrelated behavior changes unless those changes
are explicitly part of the task.

==============================================================================

SMALL, CONTROLLED CHANGES

Prefer focused refactoring steps over large uncontrolled rewrites.

Each change should have a clear purpose and remain understandable during review.

Avoid combining a major architectural rewrite with unrelated cleanup unless
there is a strong technical reason.

==============================================================================

BEHAVIOR PRESERVATION

Before refactoring, identify the behavior that must remain unchanged.

This includes:

Public APIs.

File formats.

Plugin contracts.

User-visible behavior.

Import/export compatibility.

World data integrity.

Important performance characteristics.

When behavior intentionally changes, document that change separately rather than
hiding it inside a refactor.

==============================================================================

TESTS BEFORE REFACTORING

Where practical, existing behavior should be covered by tests before significant
refactoring begins.

Tests provide a safety net against accidental behavior changes.

If suitable tests do not exist, adding characterization tests may be preferable
to refactoring blindly.

==============================================================================

DUPLICATED CODE

Remove duplication when doing so makes the architecture clearer.

Do not create abstractions solely because two pieces of code currently look
similar.

Duplication may be preferable when two operations have different responsibilities
or are likely to evolve independently.

==============================================================================

ABSTRACTIONS

New abstractions should have a clear responsibility.

Avoid:

Over-engineered helper layers.

Unnecessary interfaces.

Generic frameworks created for one use case.

Deep inheritance hierarchies.

Abstractions that hide simple operations without providing meaningful value.

==============================================================================

DEAD CODE

Unused code should normally be removed rather than preserved indefinitely.

Before removing code, verify that it is not used through:

Plugin APIs.

Reflection.

Serialization.

Configuration.

Build tooling.

External integrations.

==============================================================================

PUBLIC APIs

Refactoring public APIs requires additional care.

Do not silently rename, remove or change public interfaces when compatibility is
expected.

Use the project's deprecation and versioning procedures when an API must change.

==============================================================================

FILE FORMATS

Internal refactoring must not accidentally change serialized world data or
documented file formats.

Minecraft compatibility and Bloxd.io compatibility must be preserved.

Bloxd.io schematic generation must continue respecting the maximum of
200 chunks per `.bloxdschem` file.

Larger structures must remain partitionable into multiple schematic files.

==============================================================================

PERFORMANCE-SENSITIVE CODE

Do not assume that cleaner-looking code is automatically faster.

Refactoring rendering, chunk processing, voxel editing, import/export or other
hot paths should consider:

Allocations.

Copies.

Cache behavior.

Algorithmic complexity.

Task scheduling.

Memory usage.

Benchmark results where appropriate.

==============================================================================

REFACTORING AND BUG FIXES

If a refactor exposes a bug, separate the behavioral correction from the
structural cleanup when practical.

This makes reviews, testing and regression analysis easier.

==============================================================================

COMMIT STRUCTURE

Large refactors should be divided into logically meaningful commits where the
development workflow allows it.

Avoid mixing formatting-only changes with substantial behavioral modifications.

==============================================================================

DESIGN OBJECTIVE

Refactoring should steadily improve the codebase while keeping behavior
controlled, reviewable and testable.

==============================================================================

END OF CODING STANDARDS — REFACTORING
