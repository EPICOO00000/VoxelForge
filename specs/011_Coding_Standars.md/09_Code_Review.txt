==============================================================================
CODING STANDARDS — CODE REVIEW
==============================================================================

Code review is required to maintain correctness, consistency, compatibility and
long-term maintainability across VoxelForge.

==============================================================================

GENERAL PRINCIPLE

A code review should verify behavior and design, not merely formatting.

Reviewers should focus on whether the change is:

Correct.

Understandable.

Compatible.

Testable.

Maintainable.

Consistent with the architecture.

==============================================================================

SCOPE

Every review should consider the complete change rather than isolated lines.

Reviewers should understand:

What problem the change solves.

Which subsystem is affected.

Which interfaces are changed.

Which assumptions are introduced.

Which existing behavior may be affected.

==============================================================================

CORRECTNESS

Reviewers should verify:

Expected behavior.

Edge cases.

Failure paths.

Boundary conditions.

State transitions.

Data ownership.

Resource lifetime.

Concurrency assumptions where relevant.

==============================================================================

ARCHITECTURE

Changes must respect subsystem boundaries.

A change should not introduce unnecessary dependencies between unrelated
systems.

Public interfaces should remain consistent with the architecture and API
specifications.

==============================================================================

PERFORMANCE

Reviewers should consider performance implications when changes affect:

Rendering.

Chunk processing.

Voxel editing.

World loading.

World saving.

Import/export.

Block lookup.

Memory usage.

Multithreading.

Performance-sensitive code should avoid unnecessary allocations and repeated
expensive work.

Optimization decisions should be supported by evidence when practical.

==============================================================================

MEMORY

Reviewers should look for:

Unnecessary copies.

Unbounded allocations.

Leaked resources.

Incorrect ownership.

Long-lived references.

Large temporary buffers.

Special attention should be given to large voxel and chunk datasets.

==============================================================================

THREADING

Changes involving asynchronous or parallel execution must be reviewed for:

Race Conditions.

Deadlocks.

Unsafe Shared State.

Incorrect Thread Affinity.

Task Lifetime.

Cancellation.

Error Propagation.

UI Thread Access.

==============================================================================

FILE FORMATS

Changes to import/export systems must preserve documented format behavior.

Minecraft compatibility must not be unintentionally broken.

Bloxd.io `.bloxdschem` handling must preserve the documented 200-chunk maximum
per schematic.

Exports larger than that limit must be split into multiple schematic files
rather than silently truncated.

==============================================================================

PLUGIN COMPATIBILITY

Changes to public plugin interfaces require particular care.

Reviewers should consider:

Backward Compatibility.

API Contracts.

Versioning.

Lifecycle Behavior.

Error Isolation.

Security.

Plugin Registration.

==============================================================================

ERROR HANDLING

Reviewers must verify that failures are:

Detected.

Propagated appropriately.

Reported correctly.

Cleaned up safely.

Not silently ignored.

Partial operations must not leave invalid application state.

==============================================================================

TESTING

A review should verify that appropriate tests exist or are added for the
changed behavior.

Tests should cover important edge cases and failure conditions, not only the
successful path.

Changes affecting public APIs should include appropriate compatibility or
integration coverage where required.

==============================================================================

READABILITY

Code should be understandable without excessive explanation.

Reviewers should question:

Unnecessary complexity.

Deep nesting.

Ambiguous names.

Duplicated logic.

Unclear ownership.

Overly large functions.

Unnecessary abstractions.

==============================================================================

DOCUMENTATION

Changes that modify documented behavior must update the relevant documentation.

API changes, format changes and important architectural changes must not leave
documentation describing obsolete behavior.

==============================================================================

REVIEW COMMENTS

Review comments should be:

Specific.

Actionable.

Respectful.

Relevant to the change.

Avoid personal preferences that have no impact on correctness, consistency or
maintainability.

==============================================================================

APPROVAL

Approval means the reviewer considers the change acceptable within the project's
current standards and architecture.

Approval does not mean the code can never be improved later.

==============================================================================

DESIGN OBJECTIVE

Code review should prevent defects before they become part of the shared
codebase while keeping development efficient and collaborative.

==============================================================================
