==============================================================================
CODING STANDARDS — OVERVIEW
==============================================================================

VoxelForge coding standards define the common rules used throughout the
project's source code.

The goal is to keep the codebase:

- Readable.
- Predictable.
- Maintainable.
- Testable.
- Performant.
- Consistent across subsystems.
- Safe to extend.

These standards apply to core VoxelForge code, tools, tests and plugin-facing
implementations where applicable.

==============================================================================

GENERAL PRINCIPLES

Code should favor clarity over unnecessary cleverness.

Implementations should remain as simple as possible while satisfying the
required behavior.

Each subsystem should have clear ownership of its data and responsibilities.

Code must use public interfaces when interacting with another subsystem instead
of depending on private implementation details.

Examples include:

- Renderer access through the Renderer API.
- World access through the VoxelWorld API.
- Brush operations through the Brush System.
- Block information through the Block Database.
- Plugin functionality through the Plugin API.

==============================================================================

ARCHITECTURAL CONSISTENCY

New code must respect the architecture defined by the main specifications.

A local optimization or convenience must not introduce an architectural
dependency that bypasses subsystem boundaries.

For example, rendering code must not become responsible for importing files,
and import/export code must not require the Renderer to operate.

==============================================================================

DATA OWNERSHIP

Every piece of mutable data should have a clearly defined owner.

Code must not create hidden duplicate sources of truth.

When data is shared between systems, the sharing mechanism must be explicit and
documented where necessary.

==============================================================================

ERROR HANDLING

Errors must be handled deliberately.

Code must not silently ignore failures that can affect:

- World correctness.
- File integrity.
- Plugin state.
- User data.
- Rendering correctness.
- Application stability.

Errors should contain enough context to diagnose the problem without exposing
unnecessary sensitive information.

==============================================================================

PERFORMANCE

Performance-sensitive code must avoid unnecessary:

- Allocations.
- Copies.
- Synchronization.
- File I/O.
- GPU uploads.
- Recalculation.
- Work performed every frame.

Optimizations must preserve correctness and maintainability.

Performance assumptions should be validated through profiling or benchmarks
rather than speculation.

==============================================================================

THREADING

Threading behavior must be explicit.

Code must respect the ownership and thread-safety guarantees of the subsystem
it interacts with.

UI operations must remain on the appropriate UI thread.

Background work should use the project's task and scheduling systems where
appropriate.

==============================================================================

TESTABILITY

New functionality should be designed so that important behavior can be tested
independently.

Code should avoid unnecessary global state and hidden dependencies that make
testing difficult.

==============================================================================

DOCUMENTATION

Public APIs and non-obvious behavior must be documented.

Documentation should explain intent and constraints rather than simply
repeating what the code already makes obvious.

==============================================================================

COMPATIBILITY

Code involved in file formats and external integrations must preserve the
compatibility requirements defined by their specifications.

This includes Minecraft compatibility and Bloxd.io schematic compatibility.

Bloxd.io schematic exports must respect the maximum of 200 chunks per schematic
and split larger exports into multiple schematic files.

==============================================================================

CODE REVIEW

Code must be reviewed for:

- Correctness.
- Architecture.
- Readability.
- Error handling.
- Performance.
- Thread safety.
- Tests.
- Documentation.
- Compatibility.

==============================================================================

DESIGN OBJECTIVE

VoxelForge code should remain understandable to another developer years after
the original implementation was written.

Consistency and correctness take priority over unnecessary complexity.

==============================================================================

END OF CODING STANDARDS — OVERVIEW
