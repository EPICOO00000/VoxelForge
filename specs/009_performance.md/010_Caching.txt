==============================================================================
CACHING
==============================================================================

Caching may be used in VoxelForge to avoid repeating expensive computations.

Every cache must have a clear purpose, ownership model and invalidation strategy.

==============================================================================

CACHE OBJECTIVES

Caching should reduce:

Repeated Computation.

Repeated Data Conversion.

Repeated Memory Allocation.

Repeated Resource Loading.

==============================================================================

CACHE JUSTIFICATION

A cache should only be introduced when the cost of recomputing the data justifies
the additional memory and management complexity.

Caching must not be introduced solely because a value can technically be cached.

==============================================================================

OWNERSHIP

Every cache must have a clearly defined owner.

The owning subsystem is responsible for:

Creating Cached Data.

Updating Cached Data.

Invalidating Cached Data.

Releasing Cached Data.

==============================================================================

CACHE VALIDITY

Every cache must have an explicit definition of when its contents are valid.

A cache must never return stale data when the caller expects current state.

==============================================================================

INVALIDATION

Cache invalidation must occur whenever the source data changes in a way that
affects the cached result.

Invalidation rules must be deterministic and testable.

==============================================================================

VOXEL DATA

Voxel-derived caches may include information such as:

Derived Chunk Data.

Mesh Data.

Spatial Queries.

Precomputed Masks.

Other Derived Results.

Cached voxel-derived data must never become the authoritative source of world
state unless explicitly defined by the architecture.

==============================================================================

RENDERING CACHE

Renderer caches may retain generated rendering resources while their source data
remains valid.

World modifications that affect rendered results must invalidate the appropriate
rendering cache entries.

==============================================================================

BRUSH CACHE

Brush-related data such as reusable masks may be cached when the brush parameters
remain unchanged.

The cache must be invalidated when any parameter affecting the result changes.

==============================================================================

IMPORT AND EXPORT CACHE

Import or export processing may reuse temporary conversion data and buffers.

Persistent caching should only be used when its benefits justify its memory
cost and lifecycle complexity.

==============================================================================

MEMORY LIMITS

Caches must not grow without a defined limit.

Where appropriate, caches should define:

Maximum Size.

Eviction Strategy.

Lifetime.

Priority.

==============================================================================

EVICTION

When a cache reaches its configured limit, entries may be removed according to
an appropriate deterministic policy.

Eviction must not affect correctness.

A removed cache entry must simply be recomputable.

==============================================================================

CACHE KEYS

Cache keys must uniquely represent all inputs that affect the cached result.

Incomplete cache keys can produce incorrect results and must be avoided.

==============================================================================

CONCURRENCY

Concurrent access to caches must follow the multithreading rules.

Cache synchronization must not become a global bottleneck.

==============================================================================

DEBUGGING

Development builds may expose cache statistics including:

Hit Count.

Miss Count.

Eviction Count.

Memory Usage.

Rebuild Count.

==============================================================================

PERFORMANCE VALIDATION

A cache should be retained only when measurements demonstrate a meaningful
performance benefit.

A cache with negligible benefit but significant complexity or memory cost should
be removed.

==============================================================================

DESIGN OBJECTIVE

Caching should reduce expensive repeated work while remaining bounded,
correctly invalidated, memory-conscious and transparent to the authoritative
world state.

==============================================================================

END OF CACHING
