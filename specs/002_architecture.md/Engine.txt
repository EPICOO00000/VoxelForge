==============================================================================
VOXELFORGE ENGINE
==============================================================================

The VoxelForge Engine is the central coordinator of the entire application.

Every subsystem communicates through the Engine.

The Engine owns the project state and manages the lifetime of all major
systems.

It does not implement rendering algorithms, editing algorithms or export
logic.

Its responsibility is orchestration.

==============================================================================

PURPOSE

The Engine provides a unified entry point to every subsystem.

It guarantees that all systems remain synchronized.

It ensures that every operation follows the correct execution order.

==============================================================================

RESPONSIBILITIES

The Engine is responsible for:

Creating projects.

Opening projects.

Closing projects.

Managing the active Voxel World.

Managing active tools.

Managing active selections.

Managing undo and redo.

Managing task execution.

Managing event dispatching.

Managing subsystem initialization.

Managing subsystem shutdown.

Managing project configuration.

Coordinating communication between systems.

==============================================================================

THE ENGINE OWNS

The Engine owns exactly one instance of each global subsystem.

Examples include:

Voxel World

Brush Engine

Renderer

Task Scheduler

Event Manager

Selection Manager

History Manager

Plugin Manager

Asset Manager

Settings Manager

Import Manager

Export Manager

The Engine is responsible for creating and destroying these systems.

==============================================================================

THE ENGINE DOES NOT OWN

The Engine does not own:

Chunk data

Brush implementations

Mesh generation

Import algorithms

Export algorithms

Rendering algorithms

These belong to their dedicated subsystems.

==============================================================================

ENGINE LIFECYCLE

The Engine follows the same lifecycle for every session.

Create Engine

↓

Initialize subsystems

↓

Load project

↓

Run editing session

↓

Save if requested

↓

Shutdown subsystems

↓

Destroy Engine

==============================================================================

INITIALIZATION

Subsystems must be initialized in a deterministic order.

Each subsystem must verify that all required dependencies are available
before becoming active.

Initialization failures must be reported immediately.

==============================================================================

SHUTDOWN

Shutdown occurs in reverse initialization order.

Every subsystem must release its resources.

No subsystem should leave allocated memory or registered callbacks behind.

==============================================================================

PROJECT MANAGEMENT

The Engine manages the active project.

Only one project may be active at a time.

Opening another project automatically closes the previous one after
performing the required cleanup.

==============================================================================

ACTIVE WORLD

The Engine always exposes one active Voxel World.

Every editing operation targets this world.

Future versions may support multiple worlds, but only one can be active at
any given moment.

==============================================================================

SUBSYSTEM ACCESS

Subsystems communicate through the Engine.

Direct communication between unrelated subsystems should be avoided.

The Engine acts as the central coordinator.

==============================================================================

EVENT COORDINATION

The Engine receives events generated by the user interface,
the task system,
the renderer,
or plugins.

It forwards these events to the appropriate subsystem.

==============================================================================

TASK COORDINATION

Long-running operations should be delegated to the Task Scheduler.

The Engine remains responsive while background tasks execute.

The Engine monitors task completion and distributes results.

==============================================================================

ERROR MANAGEMENT

Critical failures should be reported to the Engine.

The Engine decides how failures are propagated to the user.

Subsystems should not terminate the application directly.

==============================================================================

STATE MANAGEMENT

The Engine maintains the global application state.

Examples include:

Current project.

Current tool.

Current selection.

Current settings.

Current active world.

Current editing mode.

==============================================================================

EXTENSIBILITY

New subsystems should integrate through the Engine.

The Engine provides stable interfaces for future expansion.

Plugins should communicate with the Engine rather than directly modifying
internal subsystem state.

==============================================================================

DESIGN PRINCIPLES

The Engine should remain:

Simple.

Predictable.

Stable.

Modular.

Easy to extend.

It should coordinate systems,
not replace them.

==============================================================================

END OF VOXELFORGE ENGINE
