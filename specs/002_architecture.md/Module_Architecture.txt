==============================================================================
MODULE ARCHITECTURE
==============================================================================

The VoxelForge architecture is composed of independent modules.

Each module has one clearly defined responsibility.

Modules communicate through public interfaces.

Internal implementations remain private.

==============================================================================

CORE

The Core module contains the internal data model of the application.

Responsibilities include:

Voxel storage

Chunk management

Selections

History

World state

The Core never depends on higher-level modules.

==============================================================================

BRUSH ENGINE

The Brush Engine converts user actions into voxel modifications.

Responsibilities include:

Brush execution

Brush shapes

Brush behaviors

Brush parameters

Brush masks

The Brush Engine only modifies voxel data.

It never generates meshes.

It never exports files.

==============================================================================

RENDERER

The Renderer converts voxel data into Blender meshes.

Responsibilities include:

Chunk mesh generation

Mesh updates

Dirty chunk rebuilding

Viewport representation

The Renderer never modifies voxel data.

==============================================================================

IMPORT SYSTEM

The Import System converts external files into the internal voxel
representation.

Supported formats are implemented as independent importers.

Each importer only performs file conversion.

==============================================================================

EXPORT SYSTEM

The Export System converts the internal voxel representation into external
formats.

Each exporter is completely independent.

Adding a new exporter must not require modifications to existing exporters.

==============================================================================

BLOCK DATABASE

The Block Database stores every available block definition.

Responsibilities include:

Universal identifiers

Game mappings

Properties

Metadata

Palettes

Version compatibility

The Block Database contains no rendering logic.

==============================================================================

ASSET SYSTEM

The Asset System manages project assets.

Examples include:

Textures

Icons

Brush presets

Palettes

Configuration files

Assets remain independent from runtime logic.

==============================================================================

TASK SYSTEM

The Task System manages long-running operations.

Responsibilities include:

Background execution

Progress reporting

Task scheduling

Cancellation

Tasks should remain independent from user interface code.

==============================================================================

EVENT SYSTEM

The Event System allows communication between independent modules.

Events notify systems about changes without creating unnecessary coupling.

Modules should react only to events relevant to their responsibility.

==============================================================================

PLUGIN SYSTEM

The Plugin System extends VoxelForge without modifying the core engine.

Plugins communicate only through the official Plugin API.

Plugins must never directly modify internal engine structures.

==============================================================================

USER INTERFACE

The User Interface provides interaction between the user and the engine.

Responsibilities include:

Panels

Sidebar

Viewport tools

Menus

Buttons

Hotkeys

The User Interface contains no business logic.

==============================================================================

UTILITIES

Utility modules provide reusable helper functionality.

Examples include:

Mathematics

Serialization

Logging

File management

Profiling

Utilities should remain generic and reusable.

==============================================================================

MODULE INDEPENDENCE

Every module should remain as independent as possible.

Changes inside one module should have minimal impact on unrelated modules.

==============================================================================

MODULE RESPONSIBILITY

Each module owns one domain of responsibility.

No responsibility should exist in multiple modules.

Duplicate responsibilities lead to maintenance problems and must be avoided.

==============================================================================

END OF MODULE ARCHITECTURE
