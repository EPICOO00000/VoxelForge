# Roadmap Overview

## Purpose

The VoxelForge roadmap defines the planned evolution of the project from the current implementation toward a mature, stable, extensible voxel editing platform.

The roadmap is a planning document. It must describe intended capabilities and priorities without overriding the technical requirements defined by the other specification categories.

Implementation decisions must remain compatible with the existing architecture, voxel-world model, renderer, brush system, block database, import/export system, UI, performance requirements, Plugin API, coding standards, and testing requirements.

## Roadmap Structure

The roadmap is organized into major development stages:

- Version 1.0.
- Version 1.1.
- Version 2.0.
- Long-term goals.
- Research.
- Known limitations.
- Future ideas.

Each version represents a target development stage rather than a guarantee that every feature will be implemented exactly as originally planned.

## Version Priorities

Development priority should generally follow this order:

1. Correctness.
2. Data integrity.
3. Stability.
4. Compatibility.
5. Performance.
6. Usability.
7. Extensibility.
8. Advanced features.

New features must not knowingly compromise the integrity of existing voxel data.

## Relationship With Existing Specifications

The roadmap does not replace detailed technical specifications.

When a roadmap item refers to a system already specified elsewhere, the implementation must follow that system's authoritative specification.

Examples include:

- Voxel storage → `003_voxel_world.md`.
- Rendering → `004_renderer.md`.
- Brush operations → `005_brush_system.md`.
- Block definitions → `006_block_database.md`.
- Import/export → `007_import_export.md`.
- UI → `008_UI_UX.md`.
- Performance → `009_performance.md`.
- Plugins → `010_PluginAPI.md`.
- Coding rules → `011_Coding_Standards.md`.
- Testing → `012_Testing.md`.

The roadmap should not introduce contradictory technical behavior.

## Compatibility Goals

VoxelForge should continue to support its documented Minecraft-compatible and Bloxd.io-compatible workflows as development progresses.

Future features must preserve compatibility unless a deliberate breaking change is documented and approved.

For Bloxd.io schematic workflows, the documented maximum of 200 chunks per `.bloxdschem` file remains an implementation constraint.

Structures larger than this limit must be represented through multiple schematic files rather than producing an invalid oversized schematic.

## Stability Rule

Features should only be considered roadmap-complete when they satisfy the project's relevant correctness and testing requirements.

A feature that works only in ideal conditions should not be considered production-ready.

## Backward Compatibility

Existing project files and supported formats should remain usable across roadmap versions whenever technically possible.

When a breaking format or API change becomes necessary, the project should provide a documented migration strategy where practical.

## Roadmap Updates

The roadmap should be updated when:

- A major feature is completed.
- A planned feature is cancelled.
- A feature is postponed.
- Priorities change.
- A technical limitation is discovered.
- A compatibility requirement changes.

Completed work must not be represented as future work.

## Guiding Principle

The roadmap should guide development without becoming a source of contradictory implementation rules.

Detailed technical specifications remain authoritative for implementation behavior.
