VOXELFORGE — VERSION 2.0
=========================

Purpose
-------
Version 2.0 represents the second major evolution of VoxelForge after the
initial stable release. It must build on the architecture, voxel world model,
renderer, brush system, block database, import/export system, UI, performance
rules, Plugin API, coding standards, and testing strategy already defined in
the preceding specifications.

Version 2.0 is not intended to replace the existing architecture without
reason. Existing systems should remain compatible wherever possible, and
breaking changes must be explicitly documented.

Core objectives
---------------
1. Improve the reliability and scalability of large voxel projects.
2. Improve Minecraft compatibility.
3. Improve Bloxd.io compatibility.
4. Expand the editing workflow without compromising performance.
5. Improve import/export reliability and validation.
6. Make large structures easier to split, manage, preview, and export.
7. Strengthen the Plugin API and extension capabilities.
8. Preserve deterministic behavior across editing, saving, loading, and
   exporting.
9. Maintain the performance requirements defined by 009_performance.
10. Maintain automated test coverage defined by 012_Testing.

Minecraft compatibility
-----------------------
Version 2.0 must continue to support Minecraft-oriented voxel workflows.

Minecraft block identifiers, states, properties, metadata, and other
format-specific information must be handled through the Block Database and
Import/Export systems rather than being duplicated inside individual tools.

Where a Minecraft format contains information that VoxelForge cannot represent
directly, the application must use an explicit compatibility policy.

Possible policies include:

- exact preservation when supported;
- conversion to the closest supported representation;
- explicit omission when the information cannot be represented;
- user-visible warning when information may be lost.

Silent destructive conversion should be avoided.

Bloxd.io compatibility
----------------------
Version 2.0 must support Bloxd.io schematic workflows.

The .bloxdschem format must remain compatible with the schema-0/version-0
structure documented by the Import/Export specification.

The implementation must respect the following characteristics:

- schematic data is divided into 32 x 32 x 32 voxel chunks;
- block payloads use the defined run-length encoding;
- chunk coordinates and dimensions must remain deterministic;
- generated files must be readable by the supported Bloxd.io workflow;
- imported Bloxd schematics must be validated before being inserted into the
  editable world.

Maximum Bloxd schematic size
----------------------------
A single Bloxd schematic must not exceed 200 chunks.

When an exported structure would exceed the 200-chunk limit, VoxelForge must
automatically split the structure into multiple schematic files or provide an
explicit split-export operation.

The split must:

- preserve the original relative coordinates;
- use deterministic chunk boundaries;
- avoid losing blocks;
- avoid duplicating blocks;
- preserve supported block information;
- provide clear naming for each generated schematic;
- provide enough metadata to reconstruct the original structure;
- warn the user when splitting is required.

The exporter must never silently create a schematic larger than the supported
200-chunk maximum.

For large structures, the preferred behavior is to partition the structure
into logical or spatially contiguous regions while keeping each generated
schematic within the limit.

Large-world workflow
--------------------
Version 2.0 should improve editing of structures significantly larger than a
single export file.

The world itself must not be artificially limited to the Bloxd schematic
limit. The 200-chunk restriction applies to an individual Bloxd schematic
export, not to the internal VoxelForge project.

Large structures should therefore be represented internally as normal
VoxelForge worlds and divided only when required by the target format.

Recommended capabilities include:

- region selection;
- chunk-based visibility;
- chunk-based loading and unloading;
- large-area copy/paste;
- region duplication;
- region export;
- multi-file export;
- export manifests;
- progress reporting;
- cancellation of long-running operations.

Export validation
-----------------
Before completing an export, VoxelForge should validate:

- dimensions;
- chunk count;
- block identifiers;
- chunk coordinates;
- encoding validity;
- target-format constraints;
- output file integrity.

If validation fails, the exporter must report the reason instead of producing a
partially valid file and claiming success.

Performance
-----------
Version 2.0 must follow the optimization principles defined in
009_performance.

Large operations should avoid unnecessary duplication of voxel data.

Long-running operations such as large imports, exports, conversions, chunk
generation, and bulk editing should be cancellable where technically
appropriate.

The UI must remain responsive during expensive operations.

Progress reporting should be based on measurable work rather than arbitrary
timers.

Backward compatibility
----------------------
Existing projects should remain loadable whenever technically possible.

If a project format must change, VoxelForge should provide:

- explicit version identification;
- migration logic where possible;
- validation after migration;
- clear error reporting when migration cannot be completed.

Plugins
-------
The Plugin API must provide a stable foundation for Version 2.0 extensions.

Plugins should not need direct access to internal renderer, memory, or storage
implementation details unless explicitly exposed by the API.

API changes must follow the versioning rules defined by the Plugin API
specification.

Testing requirements
--------------------
Every major Version 2.0 feature must have appropriate tests.

At minimum, changes affecting import/export must include:

- valid-file tests;
- invalid-file tests;
- boundary-size tests;
- large-structure tests;
- compatibility tests;
- regression tests.

The 200-chunk Bloxd schematic boundary must have dedicated tests.

A structure at the maximum supported size must export successfully.

A structure exceeding the maximum must be split correctly.

A split export must be verifiable against the original structure.

Version 2.0 success criteria
----------------------------
Version 2.0 is considered successful when:

- large voxel projects remain usable;
- Minecraft workflows remain reliable;
- Bloxd.io schematic import/export is reliable;
- the 200-chunk Bloxd schematic limit is enforced;
- oversized exports are split deterministically;
- no blocks are silently lost during splitting;
- existing functionality remains stable;
- performance remains within the defined targets;
- automated tests cover the new functionality;
- Plugin API compatibility is maintained according to its versioning rules.
