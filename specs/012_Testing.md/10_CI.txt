# CI

## Purpose

Continuous Integration (CI) ensures that VoxelForge is automatically tested whenever changes are introduced into the project.

CI must detect regressions, broken builds, incompatible APIs, failed tests, and other problems before changes are merged or released.

## General Requirements

Every CI run must:

- Build the project.
- Run the appropriate automated tests.
- Report failures clearly.
- Preserve useful logs.
- Fail when a required test or build step fails.
- Avoid silently ignoring errors.

CI must use deterministic and reproducible environments whenever possible.

## Pull Request Validation

Changes submitted for review should trigger the appropriate CI checks.

At minimum, pull request validation should include:

- Compilation/build validation.
- Unit tests.
- Integration tests.
- Relevant regression tests.
- Relevant format/compatibility tests.

Additional tests should run when the modified files affect:

- Renderer.
- Import/export.
- Block database.
- World storage.
- Plugin API.
- Performance-sensitive systems.

## Test Stages

CI should organize tests into logical stages.

### Stage 1 — Build

Verify that the project compiles successfully.

A failed build must stop the pipeline.

### Stage 2 — Fast Tests

Run tests that are suitable for frequent execution.

This stage should include:

- Unit tests.
- Fast validation tests.
- Small deterministic fixtures.

### Stage 3 — Integration

Run subsystem integration tests.

This stage should validate interactions between:

- World.
- Chunks.
- Blocks.
- Renderer.
- Import/export.
- Undo/redo.
- Plugin API.

### Stage 4 — Compatibility

Run tests for supported external formats.

This includes Minecraft-compatible workflows and Bloxd.io `.bloxdschem` workflows.

Bloxd tests must include the 200-chunk schematic limit and automatic splitting above that limit.

### Stage 5 — Extended Tests

Long-running performance and stress tests may run separately when they are too expensive for every pull request.

These tests must still run regularly before releases and after significant changes to performance-sensitive systems.

## Test Failure

A CI pipeline must fail when a required test fails.

Failures must provide enough information to determine:

- Which test failed.
- Which stage failed.
- The relevant error message.
- The relevant test fixture.
- The build or environment information required for debugging.

A failing test must not be hidden by allowing later steps to report a successful overall build.

## Flaky Tests

Tests that fail intermittently must be investigated.

A flaky test must not simply be ignored indefinitely.

If a test must temporarily be disabled, the reason must be documented and the test must remain tracked for restoration.

Tests must not be made unreliable merely to keep CI green.

## Platform Testing

If VoxelForge supports multiple platforms, CI should test each officially supported platform where practical.

Platform-specific failures must be distinguished from general application failures.

Renderer tests may require platform-specific handling when GPU behavior differs, but logical renderer tests should remain deterministic.

## Dependency Validation

CI should detect dependency or build configuration problems.

Changes to dependencies should trigger the appropriate build and test checks.

Dependency versions should remain reproducible through the project's supported dependency management system.

## Plugin API Validation

Changes to the Plugin API must trigger plugin-related tests.

CI should verify:

- API compilation.
- Plugin registration.
- Plugin lifecycle.
- API compatibility.
- Event handling.
- Invalid API usage where covered by tests.

Breaking API changes must be intentional and documented.

## Import / Export Validation

Changes to import/export systems must trigger relevant compatibility tests.

CI must validate:

- Minecraft-compatible import/export behavior.
- Bloxd.io schematic behavior.
- RLE encoding/decoding.
- Chunk coordinates.
- Dimensions.
- Round-trip behavior.
- Multi-schematic splitting.

For Bloxd.io exports:

- 200 chunks must remain valid in one schematic.
- 201 chunks must produce multiple schematics.
- No generated schematic may exceed 200 chunks.

## Artifact Handling

CI may generate artifacts such as:

- Build packages.
- Test reports.
- Logs.
- Coverage reports.
- Generated schematic fixtures.

Artifacts must be clearly identified by build or commit.

Temporary artifacts should not be treated as permanent project data.

## Test Reports

CI should make test results easy to inspect.

Reports should identify:

- Passed tests.
- Failed tests.
- Skipped tests.
- Duration where useful.
- Relevant logs.

Coverage reports may be generated when supported, but coverage percentage must not be treated as the only measure of test quality.

## Performance CI

Performance tests that are stable and inexpensive enough may run during normal CI.

More expensive benchmarks should run on a scheduled basis or during release validation.

Performance regressions must be reviewed rather than automatically ignored.

## Release Validation

Before a release is considered ready, CI should run the complete required test suite.

This should include:

- Build validation.
- Unit tests.
- Integration tests.
- Render tests.
- Regression tests.
- Compatibility tests.
- Relevant performance tests.
- Relevant stress tests.

Release validation must confirm that supported Minecraft and Bloxd.io workflows remain functional.

## Reproducibility

CI environments should be reproducible.

Builds and tests should use pinned or controlled dependency versions where appropriate.

The same source revision should produce consistent test results when executed under the same supported environment.

## CI Principle

CI is a safety mechanism for the project.

A change should not be considered complete merely because it compiles.

The required automated tests must pass before the change is treated as ready for integration or release.
