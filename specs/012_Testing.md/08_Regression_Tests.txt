# Regression Tests

## Purpose

Regression tests ensure that previously fixed bugs do not return when VoxelForge is modified, refactored, or optimized.

Every significant reproducible defect should become a regression test when practical.

## Regression Test Requirements

A regression test should:

- Reproduce the original failure conditions.
- Verify the expected corrected behavior.
- Remain deterministic.
- Be independent from unrelated tests.
- Include enough context to explain what behavior it protects.

The test should fail against the original defective behavior whenever practical.

## Bug-to-Test Process

When a bug is discovered:

1. Reproduce the issue.
2. Identify the expected behavior.
3. Create a minimal reproducible test case.
4. Confirm that the test exposes the defect.
5. Fix the implementation.
6. Confirm that the regression test passes.
7. Keep the test permanently unless the protected behavior is intentionally removed.

## World Data Regressions

Regression coverage must protect against corruption of voxel data.

Examples include:

- Incorrect block coordinates.
- Incorrect chunk coordinates.
- Blocks disappearing after save/load.
- Incorrect behavior at chunk boundaries.
- Incorrect negative-coordinate handling.
- Incorrect block replacement.
- Incorrect empty/air handling.

## Renderer Regressions

Known rendering bugs must receive dedicated regression coverage.

Examples include:

- Missing faces.
- Extra internal faces.
- Incorrect chunk-boundary geometry.
- Stale chunk meshes.
- Incorrect transparency.
- Incorrect block orientation.
- Renderer not updating after an edit.
- Incorrect rendering after loading a saved world.

## Import / Export Regressions

Import/export bugs must be preserved as regression tests.

Tests should cover previously discovered problems involving:

- Dimensions.
- Coordinates.
- Block IDs.
- Chunk placement.
- Empty regions.
- Unsupported blocks.
- Corrupted input.
- Incorrect output.
- Round-trip conversion.

## Bloxd.io Regression Tests

Bloxd.io `.bloxdschem` behavior must have dedicated regression coverage.

Regression tests must protect:

- Correct schema/header generation.
- Correct dimensions.
- Correct chunk coordinates.
- Correct 32×32×32 chunk indexing.
- Correct RLE encoding.
- Correct block IDs.
- Correct chunk serialization.
- Correct array termination.
- Correct import/export round trips.

The 200-chunk limit must also be protected.

Required regression cases include:

- 200 chunks must remain valid.
- 201 chunks must be split.
- Every resulting schematic must contain no more than 200 chunks.
- Splitting must not lose chunks.
- Splitting must not duplicate chunks.
- Re-importing all generated parts must reconstruct the original structure.

## Plugin API Regressions

Plugin API regressions must protect documented plugin contracts.

Tests should cover previously fixed problems involving:

- API method behavior.
- Plugin registration.
- Plugin lifecycle.
- Event delivery.
- API version compatibility.
- Invalid plugin input.
- Plugin shutdown and cleanup.

Changes to the Plugin API must not silently break existing supported behavior.

## Undo / Redo Regressions

Every significant undo/redo bug should receive a regression test.

Tests should verify:

- Correct restoration of previous state.
- Correct restoration of edited state after redo.
- Multi-block operations.
- Multi-chunk operations.
- Operations following import.
- Operations following large edits.

## Performance Regressions

Important performance regressions should be recorded when they represent a meaningful degradation.

Performance regression tests may protect:

- Import speed.
- Export speed.
- Chunk processing.
- Rendering.
- Large brush operations.
- Save/load.
- Schematic splitting.

Performance thresholds must allow reasonable hardware variation.

## Test Naming

Regression test names should clearly identify the behavior being protected.

Prefer:

test_bloxd_export_splits_after_200_chunks

over:

test_bug_17

If an issue tracker ID exists, it may be included in addition to a descriptive name.

## Regression Suite

Regression tests must remain part of the normal test suite.

They should not be removed merely because the original bug has not appeared recently.

A regression test may only be removed when the behavior it protects is intentionally removed or replaced and the corresponding specification is updated.

## Regression Data

Regression fixtures must be kept small where possible.

A large real-world file should only be used when the bug cannot be reproduced reliably with a smaller deterministic fixture.

Sensitive or unnecessary user data must never be committed as regression fixtures.
