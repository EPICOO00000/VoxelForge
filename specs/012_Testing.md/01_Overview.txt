==============================================================================
VOXELFORGE TESTING — OVERVIEW
==============================================================================

PURPOSE

Testing is a core part of VoxelForge development.

The test system must verify that the application behaves correctly, remains
compatible with supported workflows, and does not introduce regressions when
the codebase evolves.

Testing must cover both isolated components and complete subsystem interactions.

The objective is not simply to maximize test count. Tests must provide useful
coverage of important behavior, invariants, compatibility requirements and
failure cases.

==============================================================================

TESTING PRIORITIES

Tests should prioritize:

1. Correctness of voxel and world data.
2. Import and export compatibility.
3. Renderer correctness.
4. Brush and editing behavior.
5. Block database correctness.
6. Plugin API contracts.
7. UI-critical behavior.
8. Performance-sensitive systems.
9. Error handling and recovery.
10. Regression prevention.

==============================================================================

SUPPORTED ECOSYSTEMS

VoxelForge is designed to work with Minecraft-oriented voxel workflows and
Bloxd.io workflows.

Tests involving external formats must verify that data remains valid according
to the corresponding format specification.

Minecraft-related tests must preserve valid Minecraft-compatible data.

Bloxd.io schematic tests must preserve the expected `.bloxdschem` structure and
encoding.

A Bloxd.io schematic must never contain more than 200 chunks.

If an exported structure requires more than 200 chunks, the exporter must split
the result into multiple schematic files.

The split files must collectively represent the requested export without
silently losing or duplicating voxel data.

==============================================================================

TEST LEVELS

VoxelForge tests are organized into several levels.

UNIT TESTS

Verify small, isolated pieces of logic.

Examples include:

- Block ID conversion.
- Coordinate conversion.
- Chunk indexing.
- RLE encoding and decoding.
- Brush shape calculations.
- Validation functions.
- Import/export helpers.

INTEGRATION TESTS

Verify that multiple components work together correctly.

Examples include:

- World + chunk storage.
- Brush + world editing.
- Block database + renderer.
- Importer + world representation.
- World + exporter.
- Plugin API + core systems.

SYSTEM TESTS

Verify complete workflows from the user's perspective.

Examples include:

- Create a world.
- Edit voxels.
- Save the world.
- Reopen it.
- Export a schematic.
- Import the result.
- Verify the resulting world.

==============================================================================

DETERMINISM

Tests should be deterministic whenever practical.

The same input should produce the same expected result regardless of execution
order, machine speed or unrelated application state.

Tests involving concurrency must explicitly account for allowed scheduling
differences while still validating deterministic final state where required.

==============================================================================

TEST ISOLATION

Tests should not depend unnecessarily on:

- Developer-specific paths.
- Existing user files.
- Previous test execution.
- External network services.
- Undocumented environment state.
- Manual application configuration.

Temporary test data should be created and cleaned up automatically.

==============================================================================

TEST FAILURE QUALITY

A failed test should provide enough information to identify the problem.

Useful failure information may include:

- Input parameters.
- Expected result.
- Actual result.
- Relevant coordinates.
- Chunk coordinates.
- Block IDs.
- File or format information.
- Relevant subsystem state.

Avoid tests that only report a generic failure without useful diagnostic
information.

==============================================================================

DATA INTEGRITY

Tests must pay particular attention to operations that modify voxel data.

For important transformations, verify:

- Block identity.
- Coordinates.
- Dimensions.
- Chunk boundaries.
- Empty regions.
- Negative coordinates where supported.
- Large structures.
- Metadata where applicable.

Round-trip testing should be used whenever an operation has a reversible
representation.

For example:

IMPORT -> WORLD -> EXPORT -> IMPORT

The resulting representation should preserve all behaviorally relevant data.

==============================================================================

BOUNDARY CONDITIONS

Tests must include boundary cases rather than only normal cases.

Important boundaries include:

- Empty worlds.
- One voxel.
- One block.
- Chunk boundaries.
- Adjacent chunks.
- Large worlds.
- Maximum supported schematic size.
- 200-chunk Bloxd.io schematic limit.
- More than 200 chunks.
- Invalid coordinates.
- Invalid block IDs.
- Missing files.
- Corrupted data.
- Extremely large input where resource limits apply.

==============================================================================

REGRESSION TESTING

Every significant bug that is fixed should, where practical, receive a
regression test reproducing the failure.

The test should fail against the buggy behavior and pass after the correction.

This prevents the same defect from silently returning during future refactoring.

==============================================================================

TEST ORGANIZATION

Tests should remain organized by responsibility rather than becoming one large
collection of unrelated cases.

Test names should clearly describe the behavior being verified.

Prefer names such as:

test_export_splits_at_200_chunks

over vague names such as:

test_export_case_4

==============================================================================

TESTS AND IMPLEMENTATION

Tests must verify documented behavior rather than implementation details unless
the implementation itself is a required contract.

This allows internal refactoring without unnecessarily rewriting tests.

Tests should therefore prefer observable behavior and stable interfaces.

==============================================================================

TESTING PRINCIPLE

A successful VoxelForge test suite should make it safe to improve the project.

Developers should be able to modify rendering, world storage, editing,
import/export, UI or plugin infrastructure while having confidence that
important existing behavior remains intact.

==============================================================================

END OF TESTING — OVERVIEW
