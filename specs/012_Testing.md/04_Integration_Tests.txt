# Integration Tests

## Purpose

Integration tests verify that the individual VoxelForge systems work correctly when connected together.

The goal is not to retest every internal function already covered by unit tests, but to verify the contracts between systems and confirm that real editor workflows produce the expected result.

Integration tests must cover the interaction between:

- Voxel World
- Chunk System
- Block Database
- Renderer
- Brush System
- Import / Export
- UI
- Undo / Redo
- Plugin API
- Persistence

All integration tests must use deterministic input data whenever possible.

## World and Chunk Integration

The world system must correctly create, access, modify, and unload chunks.

Tests must verify:

- Creating a new chunk.
- Loading an existing chunk.
- Modifying blocks inside a chunk.
- Accessing blocks across chunk boundaries.
- Creating neighboring chunks when required.
- Unloading chunks without losing saved data.
- Reloading chunks and preserving their previous state.

A block modification at a chunk boundary must affect the correct neighboring chunk when the operation requires it.

## Block Database Integration

The World and Block Database systems must agree on block identifiers and block definitions.

Tests must verify:

- Valid block IDs are resolved correctly.
- Invalid IDs are handled safely.
- Imported block IDs are mapped correctly.
- Block properties required by the renderer are available.
- Block properties required by brushes are available.
- Saving and loading preserves the correct block identity.

No subsystem may silently reinterpret a valid block ID as another block.

## Brush and World Integration

Brush operations must modify the authoritative world state through the normal world/chunk interfaces.

Tests must cover:

- Single block placement.
- Multi-block placement.
- Sphere brushes.
- Box brushes.
- Replace operations.
- Erase operations.
- Operations crossing chunk boundaries.
- Operations affecting multiple chunks.
- Undo after a brush operation.
- Redo after undo.

The resulting world state must be identical whether the affected region lies inside one chunk or crosses several chunks.

## Renderer and World Integration

The renderer must reflect the current authoritative world state.

Tests must verify:

- Newly placed blocks become visible.
- Removed blocks disappear.
- Modified chunks are rebuilt when necessary.
- Neighboring chunk meshes are updated when required.
- Chunk boundaries do not create incorrect geometry.
- Reloading a chunk produces the same visual result as rebuilding it.

The renderer must never become the authoritative source of voxel data.

## Import and World Integration

Imported structures must be converted into the internal VoxelForge world representation correctly.

Tests must verify:

- Correct dimensions.
- Correct world position.
- Correct chunk coordinates.
- Correct block IDs.
- Correct block placement.
- Correct empty/air regions.
- Correct handling of unsupported blocks.
- Correct handling of structures crossing chunk boundaries.

Minecraft-compatible imports and Bloxd.io-compatible imports must be tested independently where their formats differ.

## Export and World Integration

Exported structures must represent the current world state.

Tests must verify:

- Correct exported dimensions.
- Correct block positions.
- Correct chunk coordinates.
- Correct block IDs.
- Correct handling of empty regions.
- Correct output for selections crossing chunk boundaries.

The exporter must read authoritative world data rather than cached renderer data.

## Bloxd.io Integration

Bloxd.io schematic export must respect the supported `.bloxdschem` format.

A Bloxd schematic is composed of 32×32×32 voxel chunks.

A single Bloxd schematic must contain no more than 200 chunks.

When an export contains more than 200 chunks, VoxelForge must automatically split it into multiple schematic files.

The split must:

- Never exceed 200 chunks per schematic.
- Preserve the original world coordinates.
- Preserve every block.
- Avoid missing chunks.
- Avoid accidental duplicated chunks.
- Produce deterministic part names.
- Allow every generated schematic to be imported independently.

Tests must specifically cover exports containing:

- 1 chunk.
- 199 chunks.
- 200 chunks.
- 201 chunks.
- More than 400 chunks.

## Import / Export Round Trip

Supported formats must be tested using round-trip workflows.

Example:

Import → World → Export → Import

The final voxel state must match the original voxel state for all information supported by the target format.

If a format cannot represent a specific VoxelForge feature, the expected loss must be explicitly documented and tested.

## Undo / Redo Integration

Undo and redo must correctly restore world state after integrated operations.

Tests must cover:

- Brush operations.
- Multi-chunk operations.
- Imported structures.
- Block replacements.
- Deletions.
- Operations crossing chunk boundaries.

Undo must restore the exact previous logical world state.

Redo must restore the exact state produced by the original operation.

## UI Integration

UI actions must call the same underlying systems used by programmatic workflows.

Tests must verify:

- Block selection.
- Brush selection.
- Brush parameter changes.
- World modifications.
- Undo.
- Redo.
- Import.
- Export.
- Error reporting.
- Operation cancellation where supported.

The UI must not maintain a separate authoritative copy of the voxel world.

## Failure Handling

Integration failures must not leave the world in an invalid state.

Failed operations must:

- Report the failure.
- Preserve the previous valid state whenever possible.
- Avoid partially committed edits.
- Avoid producing invalid export files.
- Provide enough diagnostic information for debugging.

## Determinism

Identical input data and identical configuration should produce identical logical results.

This applies especially to:

- Import.
- Export.
- Schematic splitting.
- Chunk generation.
- Save/load.
- Conversion between supported formats.

## Test Isolation

Integration tests must not depend on:

- Previous test execution.
- User-created worlds.
- A live Minecraft installation.
- A live Bloxd.io session.
- Network availability.
- Existing generated files.

Temporary files and generated worlds must be removed after the test completes.
