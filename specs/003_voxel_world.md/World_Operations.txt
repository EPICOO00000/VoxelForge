==============================================================================
WORLD OPERATIONS
==============================================================================

World Operations define every modification that may be applied to the Voxel
World.

All modifications must pass through the official Voxel Grid interface.

Direct modification of internal storage is prohibited.

==============================================================================

PURPOSE

World Operations provide a unified editing interface for every subsystem.

Brushes.

Importers.

Generators.

Plugins.

History.

Selections.

All modifications use the same public API.

==============================================================================

DESIGN PRINCIPLES

World Operations must remain:

Deterministic.

Atomic.

Thread-safe.

Efficient.

Independent from Blender.

==============================================================================

READ OPERATIONS

Read Operations never modify the world.

Typical read operations include:

Get Voxel.

Get Chunk.

Query Bounds.

Query Palette.

Iterate Voxels.

Iterate Chunks.

Read operations should not modify Dirty State.

==============================================================================

WRITE OPERATIONS

Write Operations modify voxel data.

Typical operations include:

Set Voxel.

Replace Voxels.

Fill Region.

Clear Region.

Paste Region.

Apply Brush.

Generate Terrain.

Import Structure.

Every Write Operation must update all affected systems.

==============================================================================

ATOMICITY

Every World Operation is atomic.

An operation either completes successfully or leaves the world unchanged.

Partial modifications are prohibited.

==============================================================================

VALIDATION

Input parameters must be validated before modification begins.

Invalid coordinates.

Invalid identifiers.

Invalid regions.

Invalid operations.

Invalid requests must never corrupt the world.

==============================================================================

DIRTY TRACKING

Successful modifications automatically update Dirty Chunks.

No subsystem should manually synchronize renderer state.

==============================================================================

HISTORY

Every reversible operation generates a History Entry.

History creation is automatic.

Subsystems should not manually construct history records.

==============================================================================

EVENTS

Successful operations generate modification events.

Interested systems may react to these events.

World Operations do not directly call Renderers or Exporters.

==============================================================================

FAILURE HANDLING

If an operation fails:

No partial modifications remain.

History is not recorded.

Dirty State remains unchanged.

Events are not dispatched.

==============================================================================

PERFORMANCE

Operations should minimize allocations.

Bulk operations should process data collectively whenever possible.

Repeated single-voxel operations should be avoided when bulk processing is
available.

==============================================================================

EXTENSIBILITY

New operation types should integrate through the existing World Operation
interfaces.

Existing systems should require minimal modification.

==============================================================================

DESIGN OBJECTIVE

Every modification of the Voxel World should be predictable, safe and
consistent regardless of the subsystem initiating it.

==============================================================================

END OF WORLD OPERATIONS
