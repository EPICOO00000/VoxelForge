==============================================================================
PLUGIN REGISTRIES
==============================================================================

Registries provide the standard mechanism through which plugins add new
extension types to VoxelForge.

A registry manages registration, identification, discovery and removal of
supported extensions.

==============================================================================

GENERAL PRINCIPLE

Each extension type should have a clearly defined registry.

A registry must have one authoritative owner.

Registration must occur through the documented registry API.

Plugins must not modify registry internals directly.

==============================================================================

REGISTRY RESPONSIBILITIES

A registry may be responsible for:

Registering Extensions.

Validating Extensions.

Assigning or Validating Identifiers.

Detecting Identifier Conflicts.

Finding Registered Extensions.

Removing Plugin-Owned Extensions.

Providing Registered Extensions to the appropriate subsystem.

==============================================================================

IDENTIFIERS

Every registered extension must have a stable identifier within its registry.

Identifiers must be unique within their namespace.

A plugin must not silently replace another extension using the same identifier.

Identifier conflicts must be detected and reported.

==============================================================================

PLUGIN OWNERSHIP

The registry must retain enough information to determine which plugin registered
an extension.

This allows plugin-owned extensions to be removed safely when a plugin is
disabled or unloaded.

Removing one plugin must not remove extensions belonging to another plugin.

==============================================================================

REGISTRY TYPES

VoxelForge may expose registries for supported extension types such as:

Brushes.

Blocks.

Importers.

Exporters.

UI Components.

Commands.

Tools.

Additional registries may be introduced when a stable extension point requires
them.

==============================================================================

BRUSH REGISTRY

The Brush Registry stores plugin-provided brushes.

A registered brush must provide the information required by the Brush API.

Brush execution must continue to use the normal voxel modification, History and
Event System architecture.

==============================================================================

BLOCK REGISTRY

The Block Registry provides the extension point for plugin-provided block
definitions when custom blocks are supported.

Block identifiers and definitions must remain compatible with the Block Database
rules.

Plugins must not directly modify the internal Block Database storage.

==============================================================================

IMPORT REGISTRY

The Import Registry stores supported plugin-provided importers.

An importer must declare the formats it supports.

Importers must remain independent from the Renderer.

==============================================================================

EXPORT REGISTRY

The Export Registry stores supported plugin-provided exporters.

An exporter must declare the formats it supports.

Bloxd.io exporters must respect the maximum of 200 chunks per `.bloxdschem`
file.

If the exported world exceeds that limit, the exporter must split the output
into multiple valid schematic files rather than truncating data.

==============================================================================

UI REGISTRY

The UI Registry stores plugin-provided UI extensions when supported.

UI registration must use documented UI extension interfaces.

UI extensions must not directly access private world or Renderer state.

==============================================================================

COMMAND AND TOOL REGISTRIES

Command and Tool registries may expose plugin-provided user actions.

Registered commands and tools must pass through the normal application
architecture when they modify world state.

They must not bypass Engine coordination, History or Event processing.

==============================================================================

VALIDATION

A registry should validate an extension before accepting it.

Validation may include:

Required Metadata.

Identifier Format.

Identifier Uniqueness.

API Compatibility.

Required Capabilities.

Declared Dependencies.

==============================================================================

REGISTRATION ORDER

Plugins must not rely on an accidental registration order.

When an extension requires another extension, that relationship must be explicitly
declared and validated.

==============================================================================

DUPLICATES

Duplicate registration must fail predictably.

A plugin must not overwrite an existing extension unless the registry explicitly
defines a controlled replacement mechanism.

==============================================================================

UNREGISTRATION

When a plugin is disabled or unloaded, its registered extensions must be removed
or disabled according to the lifecycle contract.

Unregistration must not leave invalid references inside VoxelForge.

==============================================================================

THREAD SAFETY

Registry thread-safety guarantees must be explicitly defined by the API.

Plugins must not modify registries concurrently unless the API explicitly
permits concurrent access.

==============================================================================

PERFORMANCE

Registry lookup should be efficient enough for its intended usage.

Frequently executed runtime operations should not repeatedly perform expensive
registry discovery when a stable reference can safely be retained.

==============================================================================

STABILITY

Registry implementation details are internal.

Plugins depend on registry interfaces and contracts, not on their underlying
storage structures.

==============================================================================

DESIGN OBJECTIVE

Registries provide a predictable and controlled mechanism for extending VoxelForge
while preserving unique ownership, identifier stability, plugin lifecycle
management and architectural boundaries.

==============================================================================

END OF PLUGIN REGISTRIES
