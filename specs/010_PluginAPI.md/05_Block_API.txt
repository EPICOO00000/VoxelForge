==============================================================================
PLUGIN API — BLOCK API
==============================================================================

The Block API provides controlled access to block definitions and block-related
operations exposed to plugins.

It allows plugins to work with voxel block information without directly
depending on the internal implementation of the Block Database.

==============================================================================

PURPOSE

The Block API provides controlled access to:

Block Identification.

Block Definitions.

Block Properties.

Block Lookup.

Block Registration where supported.

Block Compatibility Information.

==============================================================================

BLOCK IDENTIFIERS

Every block must have a stable identifier within the supported block namespace.

Plugins must use documented identifiers rather than depending on internal array
positions or implementation-specific storage indices.

Identifier conflicts must be detected by the Block Registry.

==============================================================================

BLOCK DEFINITIONS

A block definition may contain information such as:

Identifier.

Display Name.

Textures or Visual References.

Collision Properties.

Transparency.

Opacity.

Material Information.

Rendering Properties.

Other properties explicitly supported by the Block API.

The exact definition may evolve without exposing internal storage structures.

==============================================================================

BLOCK LOOKUP

Plugins may request block information through the documented Block API.

Lookup operations must return a valid API representation rather than exposing
private Block Database objects.

Unknown identifiers must be handled predictably.

==============================================================================

BLOCK REGISTRATION

When custom blocks are supported, plugins must register them through the Block
Registry.

A plugin must not directly insert or modify entries inside the internal Block
Database.

Registration must validate the block definition before it becomes available.

==============================================================================

IDENTIFIER CONFLICTS

Two blocks must not silently share the same identifier.

If a plugin attempts to register an existing identifier, registration must fail
or follow an explicitly documented replacement mechanism.

Existing block definitions must not be silently changed by another plugin.

==============================================================================

WORLD DATA

Blocks stored in the VoxelWorld must use the established block representation.

Plugins must not create incompatible block representations that bypass the
VoxelWorld and Block Database architecture.

==============================================================================

MINECRAFT COMPATIBILITY

Minecraft-compatible block identifiers and properties must remain consistent
with the relevant Minecraft import/export rules.

Plugins working with Minecraft data must not silently reinterpret existing block
identifiers.

==============================================================================

BLOXD.IO COMPATIBILITY

Block information used in Bloxd.io workflows must remain compatible with the
supported Bloxd.io conversion and schematic systems.

Exported `.bloxdschem` data must use valid block identifiers.

A schematic containing more than 200 chunks must be divided into multiple
schematic files rather than exceeding the supported maximum.

==============================================================================

RENDERING

Block definitions may provide rendering-related information through the
documented API.

Plugins must not directly manipulate private Renderer structures.

Rendering systems remain responsible for converting block information into
renderable data.

==============================================================================

BRUSH INTEGRATION

Custom brushes may use the Block API to select or place blocks.

Brushes must use the normal world-editing mechanisms when changing block data.

==============================================================================

PERFORMANCE

Repeated block lookups in performance-sensitive operations should use the
appropriate API mechanisms for efficient access.

Plugins should avoid repeatedly requesting identical metadata when a stable
reference or cached API representation is explicitly supported.

==============================================================================

THREADING

The API must define whether block queries and registration operations are
thread-safe.

Plugins must respect these guarantees.

Registration should normally occur during the appropriate plugin lifecycle stage
rather than during arbitrary world-editing operations.

==============================================================================

LIFECYCLE

Plugin-owned block definitions must follow the Plugin API lifecycle rules.

If a plugin providing blocks is disabled, VoxelForge must handle existing world
data according to the supported block lifecycle and compatibility rules.

A plugin must not remove a block definition in a way that silently corrupts
existing world data.

==============================================================================

SECURITY

Block definitions supplied by plugins must be validated before registration.

Plugin-provided metadata must not be allowed to bypass API validation or expose
private application state.

==============================================================================

DESIGN OBJECTIVE

The Block API provides a stable abstraction for working with blocks while
preserving Block Database ownership, world correctness, renderer separation and
Minecraft/Bloxd.io compatibility.

==============================================================================

END OF BLOCK API
