==============================================================================
PLUGIN API — BRUSH API
==============================================================================

The Brush API allows plugins to create and register custom voxel brushes.

A plugin brush is an extension of the standard VoxelForge Brush System and must
follow the same world modification, history, event and threading rules as
built-in brushes.

==============================================================================

PURPOSE

The Brush API provides controlled access to:

Brush Registration.

Brush Metadata.

Brush Configuration.

Brush Execution.

Selection Information.

Voxel Modification.

Brush Events.

==============================================================================

BRUSH DEFINITION

A custom brush should provide:

Unique Identifier.

Display Name.

Description.

Optional Icon.

Configuration Parameters.

Execution Logic.

Supported Operation Modes where applicable.

The definition must be registered through the Brush Registry.

==============================================================================

BRUSH EXECUTION

When a brush is executed, it receives the information required to determine the
affected voxel region and perform the requested operation.

The brush must only modify voxels through the documented world-editing API.

Direct modification of internal chunk storage is forbidden unless explicitly
supported by the API.

==============================================================================

WORLD MODIFICATION

Brushes must respect:

Voxel Coordinates.

Chunk Boundaries.

World Ownership.

Block Database Rules.

History.

Events.

Dirty-State Tracking.

Rendering Invalidation.

A successful brush operation must leave the world in a consistent state.

==============================================================================

HISTORY

Plugin brushes must integrate with the History System.

User-visible world modifications must be undoable and redoable when the normal
operation supports undo/redo.

A plugin must not bypass History simply because it uses custom execution logic.

==============================================================================

EVENTS

Brush operations must generate the appropriate events through the standard
VoxelForge Event System.

Plugins must not manually reproduce internal event behavior when the documented
API already provides the required mechanism.

==============================================================================

SELECTIONS

Brushes may operate on the current selection when the API provides selection
information.

The brush must respect the active selection boundaries.

Voxels outside the permitted operation region must not be modified.

==============================================================================

CONFIGURATION

Brushes may expose configurable parameters such as:

Radius.

Shape.

Strength.

Mode.

Falloff.

Block Type.

Pattern.

Custom Plugin Parameters.

Parameters must be validated before execution.

Invalid values must not corrupt world state.

==============================================================================

PERFORMANCE

Brushes may affect large voxel regions.

Implementations should avoid unnecessary work outside the affected region.

Large operations should use appropriate task or batch APIs when available.

A plugin must not block the UI unnecessarily during expensive operations.

==============================================================================

THREADING

The Brush API must clearly define which execution context is allowed.

A plugin must not access thread-sensitive VoxelForge services from an
unauthorized thread.

Long-running brush operations should use the supported task system when
appropriate.

==============================================================================

MINECRAFT COMPATIBILITY

Brushes must preserve valid Minecraft block data when operating on Minecraft
worlds or Minecraft-compatible data.

Block identifiers must be obtained through the documented Block API or Block
Database interfaces.

==============================================================================

BLOXD.IO COMPATIBILITY

Brushes may create worlds that are later exported to Bloxd.io.

Brush operations must therefore preserve valid voxel and coordinate data.

When such data is exported to `.bloxdschem`, the Export System must respect the
200-chunk maximum per schematic and split larger results into multiple files.

==============================================================================

ERROR HANDLING

A brush failure must not leave partially modified world state when the operation
cannot be completed safely.

Where transactional behavior is supported, failed operations should be rolled
back according to the operation contract.

Errors must be reported through the appropriate diagnostic or notification
mechanism.

==============================================================================

REGISTRATION

Brushes are registered through the Brush Registry.

Registration must use a unique identifier.

A plugin must not overwrite another plugin's brush without an explicitly
supported replacement mechanism.

==============================================================================

LIFECYCLE

Plugin-owned brushes must be registered during the appropriate plugin lifecycle
stage.

When a plugin is disabled or unloaded, its brushes must be removed or disabled
according to the Plugin API lifecycle contract.

==============================================================================

DESIGN OBJECTIVE

The Brush API allows plugins to provide powerful custom voxel editing tools
while preserving the same correctness, history, event, performance and
architectural guarantees as built-in brushes.

==============================================================================

END OF BRUSH API
