==============================================================================
PLUGIN API — VERSIONING
==============================================================================

The Plugin API must evolve without unnecessarily breaking existing plugins.

Versioning defines compatibility rules between VoxelForge, the Plugin Runtime
and individual plugins.

==============================================================================

PURPOSE

Versioning covers:

API Versions.

Plugin Versions.

Compatibility.

Deprecation.

Migration.

Feature Detection.

Dependency Requirements.

==============================================================================

API VERSION

The Plugin API has a version independent from the plugin's own version.

A plugin must declare the API version it requires.

VoxelForge must verify compatibility before activating the plugin.

==============================================================================

PLUGIN VERSION

Each plugin should provide its own version.

Plugin versions identify changes to the plugin itself and must not be confused
with the VoxelForge Plugin API version.

==============================================================================

COMPATIBILITY

A plugin should declare:

Minimum Supported API Version.

Maximum Tested API Version where appropriate.

Required Plugin Dependencies.

Optional Plugin Dependencies.

The runtime must reject or warn about incompatible combinations according to
the compatibility policy.

==============================================================================

BACKWARD COMPATIBILITY

Compatible API releases should preserve existing documented behavior whenever
practical.

Existing public interfaces must not be changed silently in a way that causes
valid plugins to behave incorrectly.

==============================================================================

BREAKING CHANGES

Breaking API changes require an explicit versioning mechanism.

A breaking change must not be introduced merely by changing the implementation
behind an existing public interface.

Plugins should have a migration path whenever practical.

==============================================================================

DEPRECATION

Deprecated APIs must be clearly identified.

Where possible, deprecated APIs should continue working for a defined
compatibility period.

Documentation should identify the preferred replacement.

==============================================================================

REMOVAL

An API should not be removed immediately after deprecation unless a critical
security, correctness or architectural reason requires it.

Removal must be associated with an API version change and documented migration
information.

==============================================================================

FEATURE DETECTION

Plugins should prefer capability or feature detection when supported instead
of relying on undocumented version-specific behavior.

This allows plugins to adapt to optional functionality safely.

==============================================================================

DEPENDENCIES

Plugin dependencies must specify compatible versions or version ranges where
the dependency system supports them.

A plugin must not activate against an incompatible required dependency.

==============================================================================

REGISTRIES

Identifiers exposed through registries should remain stable across compatible
API versions.

Changing an identifier may break saved projects, configurations or plugin
references and therefore requires an explicit migration strategy.

==============================================================================

DATA COMPATIBILITY

API version changes must not silently invalidate existing world data.

Minecraft and Bloxd.io workflows must maintain their documented compatibility
rules independently of plugin API versioning.

For Bloxd.io `.bloxdschem`, the 200-chunk maximum per schematic remains a format
constraint. Larger exports must be divided into multiple schematic files.

==============================================================================

PLUGIN UPDATES

When updating a plugin, the runtime should verify:

Plugin Identifier.

Plugin Version.

Required API Version.

Dependencies.

Requested Permissions.

Compatibility.

An incompatible update must not automatically replace a working plugin without
the appropriate validation.

==============================================================================

MIGRATION

When an API change requires plugin modifications, documentation should provide:

Old API.

New API.

Behavioral Differences.

Migration Steps.

Deprecation Timeline where applicable.

==============================================================================

TESTING

Plugins targeting a new API version should be tested against the corresponding
VoxelForge version before release.

Compatibility tests should cover the APIs actually used by the plugin.

==============================================================================

DESIGN OBJECTIVE

The Versioning system provides predictable evolution of the Plugin API while
protecting plugin stability, saved data, dependencies and long-term project
compatibility.

==============================================================================

END OF VERSIONING
