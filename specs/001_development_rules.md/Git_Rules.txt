==============================================================================
GIT RULES
==============================================================================

Git is the official version control system for the VoxelForge project.

Every modification to the project must be traceable through Git.

The repository should always remain in a functional and organized state.

==============================================================================

GENERAL PRINCIPLES

Commit frequently.

Each commit should represent one logical change.

Avoid large commits containing unrelated modifications.

Small commits are easier to review, understand and revert.

==============================================================================

COMMIT QUALITY

Every commit should:

compile successfully when applicable,

keep the project in a consistent state,

avoid introducing unfinished or broken features.

Temporary debugging code should never be committed.

==============================================================================

COMMIT MESSAGES

Commit messages should be clear and descriptive.

A reader should understand the purpose of the commit without opening the
modified files.

Examples:

Add chunk palette compression

Fix greedy meshing UV generation

Refactor brush manager initialization

Avoid vague messages such as:

Update

Fix

Changes

Miscellaneous

==============================================================================

ATOMIC COMMITS

Each commit should solve a single problem.

Do not combine:

bug fixes,

new features,

refactoring,

documentation updates,

performance optimizations,

into a single commit unless they are directly related.

==============================================================================

SPECIFICATIONS

When modifying the architecture or project specifications,
the corresponding documentation should be committed together with the code.

Documentation and implementation should evolve together.

==============================================================================

BRANCHES

The main branch should always remain stable.

Experimental work should be isolated until it reaches a functional state.

Incomplete experimental code should not be merged into the main branch.

==============================================================================

FILE ORGANIZATION

Respect the project directory structure.

Do not move files without a valid architectural reason.

Do not duplicate files unnecessarily.

Unused files should be removed only after verifying that they are no longer
required.

==============================================================================

CODE REVIEWS

Before considering work complete, verify that:

the implementation follows the specifications,

no unnecessary files were added,

no obsolete files remain,

no generated files were accidentally committed,

the repository remains clean and organized.

==============================================================================

ROLLBACK SAFETY

Every commit should be reversible.

Avoid commits that combine unrelated modifications, as they make rollback
difficult.

If a feature requires multiple implementation stages,
use multiple commits.

==============================================================================

LARGE FEATURES

Large features should be developed incrementally.

Recommended order:

Specification

↓

Architecture

↓

Core implementation

↓

Secondary systems

↓

User Interface

↓

Testing

↓

Optimization

This progression keeps the project stable throughout development.

==============================================================================

PROJECT HISTORY

The Git history is part of the project's documentation.

Maintain a clean and understandable history.

Future contributors should be able to understand the evolution of the
project by reading the commit history.

==============================================================================

END OF GIT RULES
