==============================================================================
CODE QUALITY RULES
==============================================================================

Code quality is a fundamental objective of the VoxelForge project.

Every contribution should improve or preserve the overall quality of the
codebase.

Working code is not sufficient.

Code must also be understandable, maintainable and reliable.

==============================================================================

GENERAL PRINCIPLES

Every piece of code should have a clear purpose.

Avoid unnecessary complexity.

Prefer simple and robust solutions over clever implementations.

Readable code is more valuable than compact code.

==============================================================================

READABILITY

Code should be easy to read.

Names should clearly describe their purpose.

Control flow should remain obvious.

Avoid deeply nested logic whenever possible.

Future contributors should understand the code without requiring extensive
explanations.

==============================================================================

MAINTAINABILITY

Code should be written with future modifications in mind.

Avoid tightly coupled implementations.

Avoid unnecessary duplication.

Changes to one subsystem should have minimal impact on unrelated systems.

==============================================================================

CONSISTENCY

Follow existing project conventions.

Use consistent naming.

Use consistent architecture.

Use consistent design patterns.

Do not introduce multiple solutions for the same type of problem.

==============================================================================

SIMPLICITY

Keep implementations as simple as possible.

Do not solve problems that do not yet exist.

Avoid unnecessary abstractions.

Avoid unnecessary inheritance.

Avoid unnecessary design patterns.

==============================================================================

ROBUSTNESS

Code should behave predictably.

Handle invalid situations explicitly.

Do not rely on undefined behaviour.

Avoid fragile implementations.

==============================================================================

ERROR HANDLING

Errors should be handled intentionally.

Never ignore failures silently.

Error messages should clearly explain the problem.

Unexpected situations should be detected early whenever possible.

==============================================================================

REUSABILITY

Before writing new code,
determine whether an existing component can be reused.

Avoid creating multiple implementations for identical behaviour.

Promote reusable components.

==============================================================================

MODULARITY

Functions should perform one responsibility.

Classes should represent one concept.

Modules should solve one category of problems.

Large systems should be divided into smaller components with clear
responsibilities.

==============================================================================

SIDE EFFECTS

Avoid hidden side effects.

Functions should only modify what they are responsible for.

Unexpected modifications make software difficult to understand and maintain.

==============================================================================

DEAD CODE

Remove obsolete code.

Remove unused classes.

Remove unused functions.

Remove unused variables.

Do not keep disabled implementations inside the source code.

The repository should remain clean.

==============================================================================

TEMPORARY CODE

Temporary workarounds should be avoided.

If a temporary solution is unavoidable,
it must be clearly documented and scheduled for replacement.

Debugging code should never remain in production.

==============================================================================

SCALABILITY

Implementations should remain maintainable as the project grows.

Assume that future developers will extend the current systems.

Avoid designs that become difficult to modify over time.

==============================================================================

REFACTORING

Refactoring should improve at least one of the following:

Readability

Maintainability

Modularity

Performance

Memory usage

Testability

If no measurable improvement exists,
the refactoring should be reconsidered.

==============================================================================

SELF REVIEW

Before considering code complete,
verify that:

The implementation is correct.

The implementation follows the specifications.

The code remains readable.

The architecture has been respected.

No unnecessary complexity was introduced.

No duplicated logic exists.

No obsolete code remains.

==============================================================================

LONG-TERM QUALITY

Every contribution should leave the project in a better state than before.

Even small improvements contribute to the long-term health of the project.

The objective is not only to build features,
but also to build a codebase that remains understandable,
maintainable and extensible for many years.

==============================================================================

END OF CODE QUALITY RULES
